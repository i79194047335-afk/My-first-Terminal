## 1. Цель и границы

### Цель

Построить работоспособную оболочку бота: клиент API площадки, машина
состояний сделки, журнал, ограничители, панель наблюдения и режимы
безопасного прогона. Проверить взаимодействие с площадкой на демо-счёте.

### Явно НЕ входит

- Стратегия и любая логика принятия решения о направлении.
- Бэктест.
- Торговля на реальном счёте.
- Автоматический вход без подтверждения человеком (см. режимы).

### Ключевое требование — совместимость

Стратегия подключается позже **как плагин**, без правок исполнительной
части. Всё, что бот знает о стратегии, — это интерфейс `SignalSource`
(§6). Если для подключения стратегии придётся менять код исполнителя,
задача решена неверно.

## 2. Среда

**Хост:** VPS Франкфурт (тот же, где живёт терминал).

**Сеть — важный нюанс.** Разведка API делалась с ноутбука из России через
VPN-контейнер, поднятый на ЭТОМ ЖЕ VPS. То есть площадка уже видела
франкфуртский IP — тот самый, с которого пойдёт бот.

Следствия:
- IP не меняется → если `user_hash` привязан к адресу, он останется валиден.
- Из пути уходит плечо «ноутбук → Франкфурт», сетевая задержка станет
  меньше. **Все замеры задержки нужно повторить прямо с VPS** (§9).
- Если бот пойдёт мимо VPN-контейнера (напрямую с VPS) — IP тот же,
  разницы быть не должно. Проверить фактически: залогиниться и сверить,
  что сессия жива.

**Python:** 3.10 (как `lighter_feed`). Зависимости: `requests`,
`websockets` (уже есть в проекте), `beautifulsoup4` или `lxml` для разбора
HTML-ответов.

## 3. Карта API площадки

Полностью подтверждена живыми запросами 2026-08-05 (демо, USD/JPY).
Отдельный документ: `INTRADE_API_MAP.md` — положить в корень ветки.

Краткая выжимка:

| Назначение | Вызов |
|---|---|
| Вход | `POST intrade35.bar/login` — email, password, **reCAPTCHA** |
| Редирект после входа | `GET /auth/id=<user_id>&hash=<user_hash>` |
| Открыть сделку | `POST /ajax5_new.php` |
| Баланс | `POST /balance.php` |
| Процент выплаты | `POST /ajax_percent.php` |
| Результат сделки | `POST /trade_check2.php` |
| История | `POST /trade_load_more2.php` |
| История сделок (сверка UNKNOWN) | `POST /trade_load_more2.php` |
| Тумблер Реал⇄Демо (ОПАСЕН, без параметра) | `POST /user_real_trade.php` |
| Котировки | `GET intrade.bar/price_now` (домен БЕЗ «35»), публично |
| Время сервера | `wss://intrade35.bar/req_info` → `{"Time_server": …}` |

### Авторизация

После входа `user_id` и `user_hash` вшиты в HTML страницы как JS-переменные.
**Все прочие вызовы авторизуются только этой парой полей формы — cookie не
нужны.** reCAPTCHA стоит только на `/login`.

→ Браузер нужен один раз, чтобы добыть `user_hash`. Дальше чистый `requests`.

### Открытие сделки

```
POST /ajax5_new.php
user_id=…&user_hash=…&option=USDJPY&investment=2
&time=1&date=0&trade_type=sprint&status=1
```
`status`: **1 = Call (вверх), 2 = Put (вниз)**.
`option` без слэша (`USDJPY`), в котировках — со слэшем (`USD/JPY`).
Нужен маппинг символов.

Ответ — HTML-строка таблицы. Разбирается в:
`data-id` → trade_id, `data-rate` → цена входа, `data-timeopen` → unix
открытия, последний аргумент `setInterval` → unix экспирации,
`time_time_<id>` → длительность в секундах.

Ошибки приходят plain text: `''` (пусто), `error_time_18`,
`error_time_night`, `error_time_night_order`, либо строка с подстрокой
`error`. **Проверять ДО того, как считать сделку открытой.**

### ⚠ Задержка открытия ~3 секунды

| | запрос | позиция открыта | `wait` |
|---|---|---|---|
| Call | 18:04:38.3 | 18:04:41 | 3559 мс |
| Put | 18:04:45.9 | 18:04:48 | 2910 мс |

Это не сеть: `balance.php` в той же сессии — 200–270 мс.
**Цена входа фиксируется в момент открытия, а не запроса.** Экспирация —
ровно 60 с от открытия. Реальное окно: `сигнал → +3 с вход → +63 с расчёт`.

Это центральный факт всей задачи. Оболочка обязана его измерять и
записывать по каждой сделке (§9).

## 5. Машина состояний сделки

```
IDLE
 └─ сигнал ──> VALIDATING     проверка ограничителей (§7)
                  ├─ отказ ──> REJECTED (в журнал с причиной)
                  └─ ok ────> SENDING      отправлен POST /ajax5_new.php
                                 ├─ ошибка ─> FAILED (сырой ответ в журнал)
                                 └─ ok ────> OPEN
                                              trade_id, цена, время открытия
                                                │ ждём экспирацию
                                                v
                                            SETTLING
                                        опрос trade_check2.php
                                                │
                                                v
                                            CLOSED (win/loss/refund)
```

Требования:
- Из `SENDING` **нельзя** отправить второй запрос по тому же сигналу.
  Повтор при таймауте запрещён: ответ мог дойти, и получится двойная ставка.
  При неопределённости — состояние `UNKNOWN`, сверка через
  `trade_load_more2.php`, а не слепой ретрай.
- Каждый переход пишется в журнал с меткой времени.
- `SETTLING` начинает опрос не раньше `expiry_ts` по времени **сервера**.

## 6. Интерфейс стратегии — главный контракт

Это то, ради чего строится оболочка. Менять его позже будет дорого,
поэтому проектировать сразу.

```python
# bot/strategy/base.py
from dataclasses import dataclass, field
from typing import Optional, Literal, AsyncIterator

@dataclass(frozen=True)
class Signal:
    ts: float                    # unix (сек), время возникновения сигнала
    symbol: str                  # канонический вид: "USD/JPY"
    direction: Literal["call", "put"]
    expiry_minutes: int = 1
    amount: Optional[float] = None   # None -> берётся из конфига
    source: str = ""             # кто породил: "manual", "shock", ...
    meta: dict = field(default_factory=dict)   # произвольный контекст
                                 # (сигма, форма, origin — что угодно)

class SignalSource:
    """Источник сигналов. Стратегия реализует ЭТОТ интерфейс и больше ничего."""

    name: str

    async def start(self) -> None: ...
    async def stop(self) -> None: ...

    def __aiter__(self) -> AsyncIterator[Signal]: ...
    # выдаёт сигналы по мере появления
```

Правила:
- Ядро (`engine.py`) знает **только** `SignalSource` и `Signal`.
  Ни одной ссылки на конкретную стратегию.
- Источников может быть несколько одновременно, они мультиплексируются.
  Каждый помечает себя в `Signal.source`.
- `meta` — свободный словарь, ядро в него не заглядывает, но целиком
  пишет в журнал. Так стратегия сможет позже разложить результаты по
  своим признакам без изменения схемы.
- Реализуемые сейчас источники:
  - `manual.py` — сигнал по нажатию кнопки в панели. Эталон и тестовый
    инструмент.
  - `hub_feed.py` — подписка на WS хаба, каркас: принимает сообщения,
    но **никакой логики направления не содержит**. Задел под будущее
    подключение детектора всплесков (он живёт на ветке `hypothesis`,
    в master его пока нет — не тянуть).

Проверка правильности: чтобы подключить стратегию, должно хватить нового
файла в `bot/strategy/` и строки в конфиге.

## 7. Ограничители (risk.py)

Все — из конфига, все проверяются до отправки, каждое срабатывание в журнал.

| Ограничитель | Смысл |
|---|---|
| `max_trades_per_day` | потолок числа сделок в сутки |
| `max_concurrent` | сколько сделок одновременно открыто |
| `cooldown_sec` | минимальный интервал между сделками |
| `max_consecutive_losses` | стоп после N убытков подряд |
| `max_daily_loss` | стоп при просадке за день |
| `allowed_hours` | окна, когда торговля разрешена |
| `min_payout_percent` | не входить, если выплата ниже порога |
| `symbol_whitelist` | разрешённые инструменты |

Дополнительно:
- **Kill-switch:** наличие файла `bot/STOP` мгновенно запрещает новые входы
  (существующие доводятся до расчёта). Проверять перед каждой отправкой.
- **Окна тишины:** переиспользовать `core/news_windows.py`, если он доступен
  в текущей ветке; если нет — оставить точку подключения и заглушку.
- Сработавший стоп-ограничитель НЕ снимается автоматически: требуется
  перезапуск или явное действие в панели.

## 8. Режимы работы

Задаются в конфиге, по умолчанию — самый безопасный.

| Режим | Что делает |
|---|---|
| `dry` | **по умолчанию.** К площадке не ходит вообще. Сделки имитируются по котировкам `price_now`, задержка моделируется. Для отладки логики. |
| `shadow` | Реальные котировки и реальный вход в API **не выполняется**: бот пишет в журнал, что он БЫ сделал. Проверка потока без ставок. |
| `demo` | Реальные запросы на демо-счёт. Основной режим этой задачи. |
| `live` | Реальный счёт. **Заблокирован**: требует и флага в конфиге, и переменной окружения, и подтверждения в панели. В этой задаче не включается и не тестируется. |

Режим печатается в лог при старте и постоянно виден в панели крупно.

| `request_ts` | когда ушёл POST |
| `open_ts` | `data-timeopen` от площадки |
| `expiry_ts` | из ответа |
| `entry_price` | `data-rate` |
| `quote_at_signal` | цена `price_now` в момент сигнала |
| `quote_at_request` | цена в момент отправки |
| **`latency_ms`** | `open_ts − request_ts` — ключевая метрика |
| `payout_percent` | на момент входа |
| `result` | win / loss / refund / unknown |
| `pnl` | |
| `raw_response` | сырой ответ площадки целиком |

практический результат всей работы: если задержка на волатильности растёт,
минутная экспирация может оказаться неприменимой в принципе, и узнать это
надо до написания стратегии.

## 11. Порядок работ (слоями, каждый — свой коммит)

**Слой 1. Клиент API.**
`api/` целиком, без торговли: логин/добыча хеша, баланс, процент выплаты,
котировки, время сервера. Проверка: скрипт печатает баланс, выплату и
сверяет время сервера с локальным.
*Приёмка:* хеш добыт, баланс получен, расхождение часов измерено.

**Слой 2. Журнал и конфиг.** Схема БД, загрузка конфига, kill-switch.

**Слой 3. Машина состояний в режиме `dry`.** Полный цикл на имитации,
без сети. Тесты на все переходы, включая `UNKNOWN`.

**Слой 4. Ограничители.** Все из §7 + тесты на каждый.

**Слой 5. Интерфейс стратегии + `manual`.** Ручной сигнал доходит до
исполнителя. Тест: подставная стратегия-заглушка работает без правок ядра.

**Слой 6. Панель.** Наблюдение, кнопки, STOP.

**Слой 7. Режим `demo` — живое взаимодействие.**
Серия одиночных сделок минимального размера. Замер задержки, проверка
разбора ответов, проверка `trade_check2.php` на расчёте.
*Приёмка:* 20+ сделок туда-обратно, все корректно разобраны и записаны,
отчёт по задержке построен.

**Слой 8. Каркас `hub_feed`.** Подписка на хаб без логики направления.

логировать сырой ответ при каждом сбое обязательно.
